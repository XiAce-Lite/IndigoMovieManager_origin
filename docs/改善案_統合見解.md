## 2. プログラム概要（両者一致・変更なし）

**IndigoMovieManager** は、WhiteBrowser 互換を目指した Windows 向け動画管理ツール（.NET 8 / WPF）。

- SQLite 管理ファイル（`.wb`）とサムネイル資産をなるべくそのまま利用
- Indigo ネイティブ WPF スキン + WhiteBrowser HTML スキン（WebView2）の二系統
- OpenCV / FFmpeg によるサムネ生成、タグ・検索・監視フォルダ・ブックマーク

### 参照 DB（`Xドライブ用.wb`）

| テーブル | 件数 |
|----------|------|
| movie | 4,773 |
| bookmark | 20 |
| watch | 5 |
| history | 14 |
| tagbar | 20 |
| findfact | 6,468 |

- `system.skin`: `DefaultSmall`
- `system.thum`: `M:\IndigoMovieManager\thumb\Xドライブ用`
- タグは `movie.tag` に改行区切りテキスト

### テスト

Release ビルドで **204 件すべて合格**（約 37 秒）。ただし UI・スキン・実プレイヤー連携はほぼカバー外。

## 3. 設計思想（両者一致）

1. **互換性最優先** — WhiteBrowser 資産の救出が中心
2. **God Object からの漸進的分離** — `Thumbnail/` `Services/` への切り出しが進行中
3. **薄い ViewModel + コードビハインド** — 全面 MVVM ではない
4. **テストは純粋ロジックに集中** — サムネ・フィルタ・パス解決は厚い
5. **実用主義** — Nullable 無効、DI なし、MessageBox エラー

### 本当の資産（リファクタより守るべきもの）

- ドキュメント（README / ARCHITECTURE）
- サムネパイプライン（世代管理・重複排除・キャンセル）
- WebView2 ブリッジ
- CI・SingleFile 配布
- 実 DB（4,700 件規模）での運用可能性

## 4. Grok 元案で正しかった点（採用）

- 互換最優先・漸進分離・薄い ViewModel の診断
- サムネ・ドキュメント・CI が強みという評価

- 負債の中心は MainWindow / SQLite / 命名、という診断

## 5. Cursor Pro 見解で修正した点（採用）

### 5.1 優先度の付け替え

Grok 元案は「きれいなコードベースを作る計画」寄りだった。個人向けで完成度の高いツールとしては、以下は**早すぎ・大きすぎ**。

| 項目 | Grok 元案 | 統合後 |
|------|-----------|--------|
| MainWindow ビッグバン分割 | P0 | **後回し**（機能周辺の局所分割のみ） |
| Dapper / Microsoft.Data.Sqlite | Phase 2 | **不要（痛みが出たら）** |
| FTS5・ページング | P1 | **後回し**（4,773 件では不要） |
| `{WHERE}` AST ホワイトリスト | P2 | **不要**（禁止トークンで十分） |
| `MovieRecords` 型変更 | P1 | **最後**（ソート・WB 互換で回帰しやすい） |
| ViewModel 大統合・DI | P2〜P3 | **後回し〜不要** |

### 5.2 プロダクト視点の追加（Grok 元案の漏れ）

ARCHITECTURE.md に明記の WB 未接続を P0 候補に含める。

| 未接続・制限 | 影響 |
|--------------|------|
| `showContextMenu` | WB スキン一覧の右クリック不可 |
| `copy` / `move` / `makeThum` / `updateInfo` 等 | `default` で空返却 |
| 一覧右クリック全般 | Indigo スキンでは可、WB では不可 |

**判断基準**:

- 困っているのが「保守しづらい」→ リファクタ優先
- 困っているのが「WB でできていた操作が足りない」「特定バグ」→ **P0 は機能・バグ側**

### 5.3 MainWindow 分割の進め方

- Grok 元案の「Phase 1 で 1〜2 週間、SearchController から」は**楽観的**
- スキン切替・サムネ再起動・フィルタ世代管理と絡み、壊しやすい
- **Thumbnail 分離と同じ粒度**で、触る機能の周辺だけ剥がす

```text
機能追加（例: showContextMenu 接続）
  → その周辺だけ ContextMenuController 化
  → 結果として MainWindow が少し薄くなる
```

## 6. Grok 統合見解で追加する点（両者の補完）

### 6.1 MainWindow 分割は「純粋な開発者体験」だけではない

WB 機能ギャップを埋める作業と MainWindow 局所分割は**表裏一体**になり得る。ビッグバンではなく**機能バックログ駆動の局所分割**が最短ルート。

### 6.2 `SQLite.cs` ファイル分割はやや前倒し可

Dapper 移行は不要でも、1,172 行の神クラスは「どこを触るか」が分かりにくい実害がある。ファイル分割は:

- 挙動を変えない
- diff が局所的
- 既存 SQL に触れない

**新機能を SQLite に足す前の前提作業**として並べてよい（専用の大規模 PR を急がない）。

### 6.3 `async void` はスタイル問題ではない

未処理例外が握りつぶされ「なぜか動かない」原因になり得る。全面分割しなくても、**触ったハンドラから `async Task` + 例外ログ**へ。ログ導入とセットが自然。

### 6.4 SQLite 二重依存は「移行」ではなく「調査」

`System.Data.SQLite` + `SQLitePCLRaw.bundle_e_sqlite3` の二重依存は、今すぐ Dapper 移行する理由にはならない。ただし SingleFile 配布で**どちらがネイティブを担うか**の整理調査はしておく価値がある。

## 7. 統合後の推奨優先順位

| 優先 | 内容 | 理由 | 出典 |
|------|------|------|------|
| **P0** | 日常で困っている WB 機能ギャップ・バグ | ユーザー価値が直接上がる | Cursor Pro |
| **P0** | 小さな `.wb` ゴールデンフィクスチャ + 読み書きスモークテスト | DB・検索・登録系を触る前の安全網 | 両者 |
| **P1** | ファイルログ（Serilog 等） | 安い・診断が楽・挙動を変えない | 両者（Cursor Pro が前倒し） |
| **P1** | 該当機能周辺の MainWindow 局所切り出し | ビッグバン分割を避ける | Cursor Pro |
| **P1** | `SQLite.cs` の機能別ファイル分割（static API 維持） | SQLite を触る作業の前提 | 両者 |
| **P2** | 新規コードのみ: 命名統一・Nullable enable（`Data/` `Services/`） | 一括リネームはしない | 両者 |
| **P2** | 触った `async void` → `async Task` + ログ | サイレント障害の防止 | Grok 補完 |
| **後回し** | Dapper 移行、FTS5、AST パーサ、DI、ViewModel 大統合 | 痛みが出てから | 両者 |
| **後回し** | MainWindow ビッグバン分割、Phase 1〜3 タイムライン | 楽観的・投資対効果低 | Cursor Pro |

## 8. 統合後の作業フロー（ロードマップの代替）

固定スケジュール（「1〜2 週間で SearchController」等）は採用しない。代わりに:

```text
1. 困りごとを決める（WB 機能 / バグ / 保守）
2. ゴールデン .wb でスモークテストを足す（DB・検索系を触る場合、まだ無ければ）
3. ログを入れる（新規エラーはファイルに残る）
4. その機能の周辺だけ MainWindow / SQLite から剥がす
5. 既存テスト + 新規スモークが通ることを確認
6. 次の困りごとへ（ビッグバン分割はしない）
```

**原則**: 各ステップで WhiteBrowser 互換を壊さない。一括リネーム・型変更・スタック刷新はしない。

## 11. 総合結論

**IndigoMovieManager_origin** は、WhiteBrowser 資産を守りながらモダン化する思想が一貫した、実用レベルで完成度の高い個人向けメディア管理ツールである。これは Grok・Cursor Pro 双方の評価で一致する。

技術的負債（MainWindow 5,400 行、SQLite 神クラス、命名混在）は事実として残るが、**最短の改善ルートは「ロードマップ通りに横展開を全部やる」ことではない**。

> **ユーザー価値のある変更のついでに、Thumbnail 分離と同じ粒度で剥がす。**

ログとゴールデンフィクスチャを足し、困っている WB 機能やバグから手を付け、リファクタはその周辺に限定する——これが統合見解の実行指針である。
